# Status da migração Rails → NestJS

Este arquivo existe para retomar o trabalho de uma sessão pra outra. Atualize-o ao final de cada sessão de trabalho.

## Contexto geral

Migrando o backend do projeto `thinktank` (monólito Ruby on Rails com front React/Inertia embutido, em `/home/pedrohdsp/Projetos/thinktank`) para este novo backend NestJS + TypeORM (`thinktank-api`), expondo uma API REST/JSON de verdade.

**Importante (orientação do usuário, 2026-09-04):**
- O código Ruby é só **referência de regras de negócio** — não precisamos seguir a estrutura, os padrões ou as bibliotecas do Rails. Se der pra implementar uma regra de forma mais simples no Nest e atingir o mesmo resultado funcional, fazer assim.
- O front (React/Inertia, já existente na mesma branch do monorepo `thinktank`) **não vai ser reescrito do zero**. A ideia é só trocar a forma como ele busca dados: hoje recebe tudo via props do Inertia, depois vai passar a chamar esta API por HTTP. Ou seja, o trabalho de front é "trocar o transporte", não recriar telas.

## Decisões arquiteturais fechadas

- API REST/JSON (não replicar o padrão Inertia).
- Autenticação via JWT: access token curto (~15min) + refresh token opaco persistido em tabela própria (`refresh_tokens`, tabela nova, não existe no Rails).
- **Mesmo banco Postgres do Rails** — este backend aponta pro mesmo banco (`thinktank_development`/`thinktank_test`, container docker `thinktank-db-1`, porta 15432). TypeORM só *mapeia* o schema existente (`synchronize: false`); nunca alterar/gerar migration que mexa nas tabelas que o Rails usa sem cuidado extra (ver "Armadilhas" abaixo).
- Chat com IA (LLM, streaming) está **fora de escopo por agora** — foco em ter algo simples funcionando primeiro.
- Arquivos continuam como bytea no Postgres (não migra pra S3 agora).
- Model `Assessment` do Rails é código morto — não portado.
- Recuperação de senha por email fica fora de escopo por enquanto.

### Fase 2 — Catálogo de referência (concluída em 2026-09-05)
CRUD completo + paginação (`?page=&per=`) pra `Chapter`, `Axis`, `Phase`, `Tool`, `Meeting`. Todos protegidos por `AuthorizationService.canManageCatalog` (novo método — mesma regra de `canManageCompanies`: só admin/secretary/super_admin; facilitator e person recebem 403, replicando `ability.rb`, que não dá nenhuma permissão a esses dois níveis sobre esses 5 models).
- `Chapter`: valida `editionYear` contra o range fechado 2023–2030 (`chapters.constants.ts`, equivalente a `Chapter::EDITION_YEARS`).
- `Axis`: CRUD simples, título+descrição obrigatórios.
- `Phase`/`Tool`: N:N entre si (`phases_tools` no Rails) implementada como entidade de junção explícita (`src/phases/entities/phase-tool.entity.ts`, registrada nos dois módulos) em vez do `@ManyToMany`/`@JoinTable` automático do TypeORM — a tabela real tem `created_at`/`updated_at` `NOT NULL` sem `DEFAULT` no Postgres, e o join table automático do TypeORM não roda os hooks de timestamp da `BaseEntity` ao inserir linhas de associação, então quebraria a constraint. Cada lado (`PhasesService`/`ToolsService`) sincroniza a relação via `toolIds`/`phaseIds` no create/update, igual o HABTM bidirecional do Rails (dá pra setar a associação a partir de qualquer um dos dois recursos).
- `Meeting`: `belongsTo` obrigatório de `Phase` (`phaseId`), segue o mesmo padrão de `User.company` (FK real com `@ManyToOne`/`@JoinColumn`, violação de FK traduzida em 422 amigável).

- **Bug corrigido durante a implementação, antes de fechar a fase:** `create`/`update` de `Phase`/`Tool` com `toolIds`/`phaseIds` inválidos persistia o registro pai mesmo respondendo 422 (a sincronização da N:N rodava *depois* do save, sem transação — um `toolId` inexistente derrubava só a segunda escrita). Corrigido envolvendo as duas escritas na mesma transação (`repository.manager.transaction(...)`), testado manualmente contra o banco real do Rails confirmando que agora nada fica órfão.
- Testado manualmente ponta-a-ponta contra o banco real do Rails (login, CRUD, unicidade, FK violation em delete, autorização de facilitator) — sem e2e automatizado ainda (a Fase 1 também não tem; só existe o e2e de `/health`).

**Entregável cumprido**, `npm run build`/`lint`/`test`/`test:e2e` passando.

### Fase 3 — Cluster, Team, Member (concluída em 2026-09-05)
CRUD completo + paginação pra `Cluster`, `Team`, e `Member` (este último exposto só como sub-recurso `/teams/:teamId/members`, sem endpoint top-level — decisão consciente do plano, não replica nested-attributes-com-`_destroy` do Rails).
- **Autorização por propriedade** (novos métodos em `AuthorizationService`: `canManageClusters/Teams/Members`, `canListOperations`, `facilitatorScopeId`, `isClusterOwner`): replica `ability.rb` — time interno (`admin/secretary/super_admin`) tem CRUD completo; **facilitator só tem leitura**, escopada a clusters onde é `facilitatorId` ou `auxiliaryFacilitatorId` (propagado pra Team via `clusterId` e pra Member via `teamId→clusterId`); person não acessa nada. Facilitator **nunca** cria/edita/remove Cluster/Team/Member — só o time interno.
- `Cluster`: `name` é computado (não é coluna), igual `Cluster#name` do Rails (`"{diaSemana} | {startTime} | {primeiroNomeFacilitador} ({anoCapitulo})"`); `weekDay` exposto como string (contrato: enums sempre como string, nunca int cru). Validações de horário (`endTime > startTime`) e data (`endDate > startDate` quando `startDate` presente) no service. Coluna `clusters.modality` (dead code no Rails) não é mapeada, igual decisão já tomada pra `clusters` na Fase 2.
- `Team`: `modality` computado a partir dos `Member`s (todos iguais / "hibrido" se misto / "Não definida" se vazio). `linkMiro`/`linkTeams` validados por regex (miro.com/teams.microsoft.com) e normalizados pra sempre `https://` antes de salvar (equivalente ao `before_save_format_links_callback`). `membersCount`/`eventsCount` (contadores do Rails via `counter_cache`) **não são mantidos** — simplificação deliberada, já que nenhuma regra de negócio que implementamos depende deles (só otimização de leitura no Rails).
- `Member`: enums `modality` (presencial/online/hibrido) e `role` (mm/mp/sol, default `sol` — sobrepõe o default `0` da coluna no Postgres, igual o Rails faz a nível de aplicação). Resposta inclui `user: {id, fullName, email}` aninhado pra evitar N+1 do front.
- **Bug real do TypeORM encontrado e corrigido (importante para as próximas fases):** combinar `leftJoinAndSelect`/`innerJoin` (qualquer join) com `.skip()/.take()` e `getManyAndCount()` no query builder **quebra a reescrita do ORDER BY paginado** (`TypeORMError`/`TypeError` no `createOrderByCombinedWithSelectExpression`), mesmo com `ORDER BY` em coluna simples (não só com `LOWER(...)`). Afetava `ClustersService`/`MembersService` (join pra carregar relação) e também — descoberto ao testar de verdade — os filtros `toolId`/`phaseId` da Fase 2 (`PhasesService`/`ToolsService`) e o escopo de facilitator em `TeamsService`, que já usavam join condicional e não tinham sido testados com o filtro realmente ativado. **Corrigido em todos os casos** trocando o join na query paginada por uma resolução prévia de IDs (via `repository.find()` na tabela relacionada + `WHERE id IN (...)`) ou, quando só precisava carregar relação (sem filtro condicional), pela API declarativa `repository.findAndCount({where, relations, order, skip, take})`. **Lição pra próximas fases:** sempre testar manualmente contra o banco real os caminhos com filtro/join condicional ativado, não só o caminho "sem filtro" — é fácil um bug desses ficar latente.
- Testado manualmente ponta-a-ponta contra o banco real do Rails: CRUD dos três recursos, validações de horário/data/link, unicidade de nome de Team, proteção de FK em delete (cluster→team→member), autorização de facilitator dono vs. não-dono, e os 4 endpoints afetados pelo bug do TypeORM acima.

**Entregável cumprido**, `npm run build`/`lint`/`test`/`test:e2e` passando.

### Fase 4 — Event, Attendance, ToolEventAssessment (concluída em 2026-09-05)
O domínio mais complexo até agora: fluxo de avaliação de evento (4 itens a-d, cada um com score+comentário), presenças, avaliação de ferramentas por evento, avaliação em lote e export CSV de pendências.
- **Contrato de endpoints:** `/events` (CRUD + filtros `teamId`/`meetingId`/`pending`), `/events/:eventId/attendances` (CRUD + `PATCH .../status` pro fluxo rápido sem validação completa), `/events/:eventId/tool-event-assessments` (CRUD) — **não** nested-attributes-com-`_destroy` do Rails, mesma decisão já tomada pra `Team.members` na Fase 3. `/teams/:teamId/team-bulk-evaluations` (`GET` lista os eventos pendentes da equipe com attendances/tool-assessments aninhados pra revisão; `PATCH` atualiza vários eventos de uma vez, cada um salvo independentemente — uma rejeição não desfaz os outros, igual o Rails). `/reports/pending-assessments.csv`.
- **Autorização (novos métodos em `AuthorizationService`): `canManageEvents`/`canCreateEvent`.** Diferente de Cluster/Team/Member (Fase 3, facilitator só lê): aqui `ability.rb` dá `can :manage` pro facilitator dono do Cluster da equipe do evento (`Event.team.cluster.facilitator_id/auxiliary_facilitator_id`) — CRUD completo, não só leitura. `can :create, Event` é **irrestrito** pro facilitator (não dá pra checar propriedade de um registro que ainda não existe). Ownership resolvida via `EventsService.getOwnershipForTeam(teamId)`, reaproveitada por Attendances/ToolEventAssessments/TeamBulkEvaluations (todas penduradas na mesma cadeia Event→Team→Cluster).
- **`Event.syncNameFromMeeting`:** o `name` do evento é sempre derivado do `Meeting` (nunca informado pelo cliente) no create, e resincronizado sempre que `meetingId` muda no update; se o update não mexe no `meetingId`, `name` pode ser setado direto.
- **Validações condicionais dos itens a-d** (`EventsService.assertAssessmentRules`): score obrigatório só quando `goToNext=true` (equivalente ao `force_assessment_validation` do Rails); comentário obrigatório quando o score resultante é pessimo/ruim/nao_se_aplica — **simplificação deliberada**: o Rails só valida isso `on: :update`, mas como o `CreateEventDto` nem expõe os campos de avaliação (evento sempre nasce sem avaliação), a regra colapsa pra "sempre no update", sem perder nada.
- **`goToNext`** (`PATCH /events/:id`): força a validação completa (scores + `EventsService.assertAttendancesRegistered`, que erra citando o nome de cada membro sem presença registrada) e, se salvar com sucesso, busca o próximo evento pendente da mesma equipe (`findNextPendingEvent`) — a resposta de update é **sempre** `{ event, nextPendingEvent }`, já que não há mais redirect HTTP como no Rails.
- **Dois enums de score diferentes, cuidado ao copiar:** `EventScore` (6 valores, com `nao_se_aplica`) vs `ToolAssessmentScore` (5 valores, sem `nao_se_aplica`) — arquivos separados de propósito.
- **`Attendance`:** único composto `(memberId, eventId)` garantido por índice único real no Postgres (traduzido de `23505`, sem precheck — mesmo padrão de CPF/RG na Fase 1); `reason` obrigatório só quando `status=absent`; `PATCH .../status` pula essa validação (`save(validate:false)` do Rails), pensado pro fluxo rápido de marcar presença/ausência numa lista.
- **`ToolEventAssessment`:** comentário obrigatório se `score` ∈ {pessimo, ruim} — **sempre**, não só em update (diferente de Event, onde a mesma regra só vale em update).
- **Simplificações deliberadas em relação ao Rails:** (1) `membersCount`/`eventsCount` (counter caches) continuam não mantidos, mesma decisão da Fase 3; (2) deletar um Event com attendances/tool-assessments vinculados é bloqueado por violação de FK (409) em vez de cascatear a exclusão como o Rails faz em código — consistente com o resto do projeto (Cluster/Team/Member também só bloqueiam, não cascateiam); (3) o CSV de pendências não replica a exclusão "não facilitado pelo usuário atual" de `pending_assessment_not_facilitated_by` (só relevante pro caso raro de um admin que também facilita um cluster) — fica restrito ao time interno via `canManageEvents`; (4) CSV gerado por um util pequeno escrito à mão (`common/utils/csv.util.ts`) em vez de puxar uma lib nova, dado que é uma única exportação plana de poucas colunas.
- Testado manualmente ponta-a-ponta contra o banco real do Rails: fluxo completo de um evento (criar → registrar presenças/ausências com e sem motivo → avaliar os 4 itens → `goToNext` bloqueando e depois liberando → checar `nextPendingEvent`), avaliação de ferramenta, violação de unicidade de presença, avaliação em lote (`team-bulk-evaluations`) com sucesso parcial, export CSV, e autorização (facilitator dono vs. não-dono, `create` irrestrito).

**Entregável cumprido**, `npm run build`/`lint`/`test`/`test:e2e` passando.

## Armadilhas já encontradas (não repetir)

1. **`migration:generate` não pode ser rodado contra as tabelas do Rails** (users, companies, etc.) — ele compara com TODO o schema do banco e propõe `DROP`/`ALTER` destrutivos porque as entidades TypeORM não mapeiam 100% dessas tabelas (colunas do Devise, índices parciais, nomes de FK do Rails). Só usar `migration:generate` pra tabelas novas (ex.: `refresh_tokens`), revisando o resultado manualmente antes de rodar.
2. **`@CreateDateColumn`/`@UpdateDateColumn` do TypeORM**: emitem `DEFAULT` no INSERT/UPDATE, contando com `DEFAULT now()` no banco — que as tabelas do Rails não têm (ActiveRecord seta timestamp em código Ruby, não via DB default). Por isso `BaseEntity` (`src/common/entities/base.entity.ts`) usa colunas simples + hooks `@BeforeInsert`/`@BeforeUpdate` pra setar os timestamps em código, igual o Rails faz.
3. **Query builder do TypeORM: join + `skip()/take()` + `getManyAndCount()` quebra o ORDER BY paginado** (ver Fase 3 acima para detalhes e o fix). Ao adicionar qualquer `findAll` com join (mesmo condicional, só ativado por um filtro opcional), usar `repository.findAndCount({relations, where, order})` (sem query builder) ou resolver a lista de IDs numa consulta separada antes — nunca `createQueryBuilder(...).innerJoin/leftJoinAndSelect(...).skip().take().getManyAndCount()`. E sempre testar manualmente o caminho com o filtro/join ativado antes de fechar a fase, não só o caminho sem filtro.
4. **O script `typeorm`/`migration:*` de `apps/api/package.json` quebrou silenciosamente com a virada pra monorepo (2026-09-05)** e só foi notado em 2026-09-06 ao escrever o passo a passo de setup no README: apontava pro caminho fixo `./node_modules/typeorm/cli.js`, que existia quando `apps/api` era a raiz do repo, mas em workspaces do npm o `typeorm` fica hasteado (hoisted) pro `node_modules` da raiz — o arquivo simplesmente não existe mais ali. Corrigido com um wrapper (`apps/api/scripts/run-typeorm-cli.mjs`) que usa `require.resolve('typeorm/cli.js')` (que sobe a árvore de `node_modules` como o Node faz de verdade) em vez do caminho fixo. Lição: depois de qualquer reestruturação de pastas/workspaces, rodar de fato os scripts que dependem de caminho relativo pra `node_modules` (não só `build`/`test`/`dev`, que não tocam nisso), não assumir que continuam funcionando.

## Monorepo (front trazido pra cá em 2026-09-05)

Por decisão do usuário, o repo virou um monorepo (npm workspaces) trazendo o front React/Inertia pra dentro dele, em vez de deixar essa etapa só pra depois:
- `apps/api/` — é o que era a raiz do repo antes (todo o conteúdo de `src/`, `test/`, configs, etc. só foi movido pra dentro dessa pasta; nenhum código do backend mudou).
- `apps/web/` — front **copiado** de `thinktank/app/frontend` (o original no repo Rails **não foi tocado/removido**, por decisão do usuário — só copiado). 142 arquivos, ~880K.

**O que foi feito nesta etapa (só reestruturação mecânica, sem adaptar nenhuma tela ainda):**
- `vite-plugin-ruby` removido do `vite.config.ts`/`package.json` do front (só existia pra integrar com o asset pipeline do Rails) e substituído por config padrão de Vite + `index.html` próprio.
- `tsconfig.json`/alias `@/*` do front ajustados pra apontar pra `apps/web/src` (era `app/frontend`) — nenhum arquivo de página precisou mudar, só a raiz do alias.
- Todas as outras dependências do front (Inertia, React, Tailwind 4, radix-ui, etc.) mantidas como estavam.
- `package.json` raiz novo com `"workspaces": ["apps/*"]` + scripts de conveniência (`dev:api`, `dev:web`, `build:api`, `build:web`, etc.).
- `.gitignore` raiz reescrito sem `/` no início dos padrões (`dist/`, `node_modules/` em vez de `/dist`, `/node_modules`) pra valer em qualquer profundidade, já que agora tem dois workspaces.
- **npm 11 passou a bloquear install scripts por padrão** (`bcrypt`, `esbuild`, `@scarf/scarf` ficaram sem rodar o script nativo no primeiro `npm install`) — precisou `npm install-scripts approve bcrypt @scarf/scarf esbuild` (isso grava um campo `allowScripts` no `package.json` raiz) + `npm rebuild bcrypt esbuild`. Se um `npm install` limpo no futuro voltar a quebrar o bcrypt (login falhando com erro de binding nativo), é isso — rodar os dois comandos de novo.

**O que ficou fora do escopo desta etapa de reestruturação** (a adaptação de verdade — trocar Inertia por rotas reais + fetch/JWT — foi feita numa etapa seguinte, na mesma sessão de 2026-09-05, ver subseção "Adaptação do front — Auth/Login" abaixo): naquele momento, nenhuma tela funcionava; agora o login já funciona, as ~19 telas restantes (companies, users, catálogo, cluster/team/member, events) continuam esperando props do Inertia e ainda não funcionam.

### Adaptação do front — Auth/Login (concluída em 2026-09-05)

Primeiro grupo de páginas migrado de verdade (Inertia → fetch/JWT), provando o padrão que as próximas ~19 telas vão seguir.

- **Roteamento:** `react-router-dom` instalado; `entrypoints/application.tsx` não usa mais `createInertiaApp` — agora é `BrowserRouter` + `AuthProvider` + `AppRoutes` (`src/routes.tsx`, só `/login` e `/` por enquanto).
- **`src/lib/api-client.ts`:** fetch wrapper único pra API inteira (sem lib nova — axios/react-query não se justificavam pro tamanho do app ainda). Guarda `accessToken`/`refreshToken` no `localStorage`, injeta `Authorization: Bearer`, e em qualquer 401 tenta um refresh automático (`POST /auth/refresh`) e repete a chamada original uma vez antes de desistir e derrubar a sessão.
- **`src/lib/auth-context.tsx`:** `AuthProvider`/`useAuth()` — restaura a sessão no load (se tiver refresh token salvo, busca `GET /users/me`), expõe `login`/`logout`. Tipo `CurrentUser` é próprio, não confundir com `types/user.ts` (esse é o shape antigo da listagem de `/users`, ainda em Inertia, vai mudar quando esse grupo for migrado).
- **`src/components/protected-route.tsx`:** gate simples (`Navigate` pra `/login` se não autenticado).
- **`pages/sessions/new.tsx`:** reescrita — era um `<form action="..." method="post">` puro pro Devise com `authenticity_token`; agora é um form controlado chamando `login()`.

### Adaptação do front — Events (concluída em 2026-09-07)

Quinto e último grupo grande, espelhando a Fase 4 (o domínio mais complexo do backend). Fechado na mesma sessão do grupo Cluster/Team/Member, a pedido do usuário ("continuar com todo o restante", "finalizar isso hoje").

- **Achado de autorização, o oposto do de Cluster/Team/Member:** conferindo `authorization.service.ts` de novo, `canManageEvents` também é só `isElevated` — **mas** o `EventsController`/`AttendancesController`/`ToolEventAssessmentsController`/`TeamBulkEvaluationsController` combinam isso com `isClusterOwner` (Event → Team → Cluster) em **todo** endpoint, inclusive o `GET` de um recurso específico. Ou seja, aqui a propriedade do facilitador dá CRUD completo, não só leitura — o oposto exato da regra de Cluster/Team/Member. Consequência prática pra UI: como o `GET` individual já exige o mesmo nível de acesso da escrita, **se a página carregou, quem está vendo já pode gerenciar tudo nela** — `events/show`, `attendances/*` e `tool-event-assessments/*` não têm nenhum gate de permissão (nenhum `canManage` condicional), só `events/index` precisa de um (`canListOperations`, porque a lista já vem escopada pelo backend pra quem é facilitador) e a criação usa `canCreateEvent` (novo em `lib/authorization.ts`, irrestrito pro facilitador — não dá pra checar propriedade de um registro que ainda não existe). **Lição confirmada duas vezes agora:** não generalizar a regra de autorização de uma fase pra outra sem conferir o `authorization.service.ts` de novo — o padrão muda por domínio.
- **`events`:** `new`/`edit` compartilham `EventForm`, mas só `edit` mostra a seção de avaliação (create não aceita os campos, igual o Rails só valida `on: :update`). Botão "Salvar e ir para o próximo evento pendente" replica o `goToNext`: o `PATCH` sempre devolve `{event, nextPendingEvent}`, e o front navega pro próximo pendente ou avisa que não sobrou nenhum. Sem "Situação: Concluído/Pendente" binária (o `happened` do Rails) — só existe `pendingAssessmentsCount` (0-4), sem contar presenças sem registro, então o badge mostra o número em vez de arriscar rótulo impreciso. "Exportar CSV" usa `apiDownload` (novo em `api-client.ts`): sem sessão de cookie, um `<a href>` puro não manda o Bearer token — o download passa pelo `fetch` com o header e vira Blob antes de "clicar" num `<a>` temporário.
- **`attendances`** (nested em `/events/:eventId/attendances`, igual já era no Rails): índice com ações rápidas Presente/Ausente (`PATCH .../status`, sem validar `reason` — mesmo fluxo rápido do Rails) além de Editar/Excluir completos.
- **`tool-event-assessments`** (pasta nova, sem tela nenhuma no Rails original — lá era só nested-attributes dentro do form de Event): `new`/`edit` geridos a partir de `events/show`, mesmo padrão de `Member` em `teams/show`.
- **`team_bulk_evaluations`:** reescrito contra `GET`/`PATCH /teams/:teamId/team-bulk-evaluations`. Só os 4 critérios + comentários gerais são editáveis em lote (`BulkUpdateEventsDto` do backend não aceita presenças/avaliações de ferramenta aninhadas — mesma decisão de não replicar nested-attributes) — presenças/ferramentas aparecem como contexto de leitura com link pra gerir de verdade. Resposta `{updated, rejected}` mapeada pra erro por card; **decisão deliberada de não dar refetch depois de salvar** (evitaria perder edições não salvas de outros cards ainda abertos) — custo: a lista de pendências só reflete um evento resolvido num reload da página, documentado no código.
- **Validado:** `npm run typecheck:web`/`build:web` limpos — **zero erros em todo o front agora**, incluindo os pré-existentes de `hrefFor` (não sobrou nenhuma tela no formato antigo). Testado via HTTP direto contra a API real, ponta a ponta: criar evento → registrar presença → avaliar ferramenta → `PATCH` com os 4 scores + `goToNext` (confirmado `nextPendingEvent: null` quando não sobra pendência) → `PATCH .../status` (fluxo rápido) → `PATCH` em lote do `team-bulk-evaluations` (confirmada a rejeição por comentário faltando, mapeada certo pro campo) → export CSV (200) → limpeza.
- **Não validado num navegador de verdade** — mesma limitação de todas as sessões anteriores.
